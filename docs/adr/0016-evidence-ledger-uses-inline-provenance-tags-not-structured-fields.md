# Evidence Ledger Uses Inline Provenance Tags, Not Structured Fields

Work Object Evidence ledger entries use an inline-tag convention: a timestamp bullet followed by a provenance tag (`[decision]`, `[system]`, `[inference]`, `[gap]`, `[testimony]`) and free text. The previously documented structured-field block — `**Provenance**:`, `**Claim**:`, `**Source**:`, `**Confidence**:`, `**Corroboration**:` — is dead documentation that was never adopted in any real Work Object and must not be used as the target format for future enforcement.

This decision was made after inspecting a real, closed Work Object with 20+ History entries. Every real evidence entry used the inline-tag convention with free text. Zero entries used the structured-field block documented in `references/EVIDENCE-MODEL.md`. The documented format was not merely unfollowed — it was the wrong shape for how evidence is actually produced. Specialists and the conductor write evidence as narrative bullets with a provenance tag because that is what fits the flow of a grilling session, a design trace, or an implementation pass. Structured fields demand a level of formality that the evidence producer does not have at the moment of capture — the producer knows the provenance and the claim, but may not know the confidence or have corroboration yet.

The inline-tag convention carries exactly what is known at capture time and nothing more. `[system]` marks machine-observable facts (file contents, git status, command output). `[decision]` marks choices explicitly accepted during a session. `[inference]` marks reasoned conclusions. `[gap]` marks acknowledged unknowns. `[testimony]` marks claims from a human source. Free text follows each tag, carrying the specific claim, source path, or observation. This convention is lightweight enough that every specialist can produce it without breaking flow and structured enough that the future CLI's gate validation can parse it — the tag provides the type classification, and the text provides the content to match against gate field-value requirements.

The alternative of keeping the structured-field block as the documented format and treating real usage as migration debt was rejected. That would mean every real Work Object's evidence entries are "wrong" relative to the documentation, and the CLI's gate validation — when built — would be designed against a format that has zero real examples to validate against. The gate design in ADR 0015 assumes the CLI will check evidence field values structurally (e.g., `result: pass`). Those checks must validate against the inline-tag convention, not a structured block that never existed in practice. The alternative of inventing a new structured format and migrating all existing entries was rejected as unnecessary abstraction without demonstrated need — the inline tags already classify provenance, which is what gates need.

The `EVIDENCE-MODEL.md` reference file must be rewritten to codify the inline-tag convention as the canonical format and to drop the structured-field block. This rewrite was completed on 2026-07-21 as part of the evidence-model component plan (Grilling Session 7, `docs/design/evidence-model-component-plan.md`). `EVIDENCE-MODEL.md` is now a thin satellite describing only Work-Object-specific attachment; the canonical tag taxonomy lives in `AGREEMENT-LOOP.md`.

This decision applies to all evidence entries in Work Object Evidence ledgers. It does not apply to History entries, which use a different format (timestamp, action, resulting state, actor type, platform, rationale). It does not apply to non-Work-Object evidence, such as memory candidate provenance or regulation session evidence, which may use different formats appropriate to their domains.

Enforcement is currently conventional — all 15 real Work Objects use the inline-tag convention organically, and no specialist or conductor has ever produced a structured-field entry. Planned enforcement is the future CLI's gate validation, which will parse evidence entries by tag and match field values against gate requirements. The CLI will not enforce that every conceivable field is present — only the fields that gates require.

Revisit this ADR when the CLI design session determines that gate validation against inline-tagged free text is insufficiently precise, when a new evidence type requires structured fields that the inline convention cannot represent, or when evidence entries are observed using tags inconsistently (e.g., `[system]` for claims that are actually `[inference]`).

Related ADRs: ADR 0015 (prerequisite gates consume evidence entries and will validate against this format).
