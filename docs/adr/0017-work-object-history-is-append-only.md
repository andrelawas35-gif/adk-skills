# Work Object History Is Append-Only

Work Object History entries are append-only. Existing entries must not be edited, deleted, reordered, or renumbered. New entries may only be appended at the end of the History section. This invariant applies regardless of the mutation mechanism — whether an agent edits the file directly, a specialist appends a transition record, or the future CLI performs a typed command.

History is the one Work Object property whose corruption is genuinely unrecoverable. State and status can be corrected by re-reading the current frontmatter. Evidence format can be normalized. Missing fields can be backfilled from context. But a History entry that was deleted, rewritten, or reworded cannot be reconstructed — the original rationale, the exact timestamp, and the sequence of actions that led to the current state are lost permanently. Every other Work Object property is either derivable (state from the most recent transition), correctable (a wrong field value), or non-critical (an advisory progression). History is the audit trail, and an audit trail with gaps or altered entries is not an audit trail.

The alternative of relying on prose instructions alone ("agents should not edit History") was rejected. Every other "documented but unenforced" property in the Work Object contract — state enum membership, status values, evidence format — has been observed to drift from its documentation. History corruption may not have been observed yet, but waiting for it to happen before adding protection is waiting for an unrecoverable event. The alternative of waiting for the full CLI to enforce History immutability was rejected because the CLI has no timeline and a corrupted History entry cannot be recovered once it occurs.

The interim enforcement mechanism is a lightweight, CLI-independent check — a script that diffs a Work Object's History section against its last-committed version and fails if any existing entry's text changed or was removed. New appended entries pass. This script extends or complements `tools/verify-conformance.py`, which already validates generated-adapter structure and is the closest existing machine-readable contract check. The script does not require the CLI to exist; it requires only that the Work Object file is under version control and that the check runs before or after mutations. If the file is not yet committed, the check has no baseline and degrades gracefully with a warning rather than a false positive.

The full mutation-enforced guarantee — the CLI rejecting any command that would alter an existing History entry — remains planned for the future CLI session. Until then, the interim script plus the agent instruction provide defense-in-depth: the script catches post-mutation corruption, and the instruction reduces pre-mutation risk.

This decision applies to the History section of all Work Objects. It does not apply to other append-only structures in the broader system — Values history, Regulation session records, or event store entries — which may have their own append-only guarantees established by separate ADRs. It does not apply to frontmatter fields, body sections other than History, or the Evidence ledger, all of which may be edited or corrected.

Revisit this ADR when the interim script is built and demonstrates that History corruption has never occurred (the check may be unnecessary overhead), when the CLI design session determines that History immutability should be enforced through a different mechanism (e.g., content-addressable storage rather than diff-based checking), or when a real History corruption event reveals a gap in the current enforcement approach.

Related ADRs: ADR 0015 (History entries record lifecycle transitions and carry rationale for each state change).
