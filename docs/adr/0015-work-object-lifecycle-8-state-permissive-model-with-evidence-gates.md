# Work Object Lifecycle Uses an 8-State Permissive Transition Model with 5 Evidence-Based Prerequisite Gates

Work Objects transition through eight states — `notice`, `explore`, `design`, `build`, `verify`, `release`, `observe`, `close` — with four independent statuses: `active`, `waiting`, `paused`, `closed`. Transitions are permissive by default: any state may transition to any other state unless explicitly prohibited. Only two transitions are prohibited: `state: close` may not transition to any other state, and `status: closed` may not transition to any other status. The permissive default avoids a full transition matrix that would be immediately wrong for real work; the narrow prohibitions protect terminal semantics without constraining legitimate paths.

Five evidence-based prerequisite gates enforce consequential transitions. Each gate specifies an evidence type, required fields, required field values, and a consequence threshold above which the gate activates. The `build` gate requires a design decision record (`type: decision`) at `high` consequence only — routine work proceeds without one. The `release` gate requires verification evidence with `result: pass` plus a deployment authority record with a `scope` field, at all consequence levels. The `close` gate requires an outcome record at all consequence levels. The `observe` gate requires either deployment or recovery evidence with `result: pass` at all consequence levels. Gates check evidence field values structurally — a `result: pass` string, not a semantic judgment about whether the evidence is convincing — because evidence semantics are a human and model judgment, not a deterministic check.

State and status are genuinely independent axes. No `(state, status)` combination is illegal. `state: close, status: active` is legitimate — it means an active outcome review is in progress. `status: closed` is always terminal regardless of `state`: the CLI, when built, will prohibit transitioning `status` from `closed` to any other value. Resuming closed work requires creating a linked successor Work Object.

Type-specific progressions are advisory metadata surfaced by `ws status` as guidance, never enforced. An `inquiry` typically moves `notice → explore → close`; a `project` moves the full chain; a `change` skips `explore`; an `incident` skips `design`. But any type may take any valid path, because real work does not follow prescribed sequences.

Closure is consequence-scaled. At `low` or `meaningful` consequence, `status: closed` requires only a `closed_reason` — the object may close from any state. At `high` consequence, closing requires routing through `state: close` first, which triggers the outcome record gate. High-consequence work always receives a recorded outcome, even on abandonment. The `closed_reason` field in frontmatter is deprecated — its information already lives in the final History entry's rationale, and duplicating it adds a field nobody populates for no information gain. `revisit_trigger` remains required when `status` is `waiting` or `paused`, since it is the one conditional field currently showing a genuine information gap in real Work Objects.

`decide` and `frame` were removed from the state list. Decision-making is an activity that can occur in any state, routed to `pressure-test-decision` when a decision is unresolved — the object stays in its current state during the decision. Framing is work done within `notice`, shaping the signal before the first transition. Removing both reduces the state count from 10 to 8 and eliminates two states whose only purpose was to name an activity.

No re-entry rules exist. When an object resumes from `waiting` or `paused`, it resumes at the same state. Whether the external condition changed during the wait is a judgment call for the human or model — no schema rule can determine that.

The lifecycle model is currently enforced through agent prose-compliance, not machine enforcement. No CLI exists yet. The CLI that will eventually own mutation, validation, and gate enforcement is deferred to a dedicated future grilling and build session. Until that session, every "CLI enforces/validates/prohibits" clause in the lifecycle specification is a target, not a description of current behavior. The conductor skill (`conduct-work-object`) and all routed specialists are expected to follow the lifecycle rules as agent self-checks, with the understanding that compliance depends on an LLM reading and choosing to follow prose instructions.

The alternative considered was a prescriptive transition matrix — every transition explicitly listed, all others prohibited. This was rejected because real work follows unpredictable paths: an `explore` object may discover it needs a design without passing through `notice` first; a `verify` object may find a gap that sends it back to `design`. A permissive default with narrow evidence-based gates captures the real constraint (some transitions need proof) without fabricating restrictions on paths that are legitimate. The alternative of type-specific states — an `incident` state, a `project` state — was rejected because it would bifurcate the routing table and specialist contracts for no benefit beyond labeling.

The `high`-consequence tier (explicit authority per transition, close-routing gate) has zero real instances across 15 active Work Objects. Its rules remain provisional-untested until a real `high`-consequence object occurs. No artificial test case will be manufactured, because misclassifying something as `high` for effects it does not actually have violates the repo's own consequence principle — consequence follows effects, not emotional intensity or urgency.

The `blocked` status was merged into `waiting`. Both meant "not progressing until something changes," and the distinction between "external condition" and "user choice to stop" is already captured by the separate `paused` status. Four statuses — `active`, `waiting`, `paused`, `closed` — cover all real Work Object states observed across 15 active objects.

This decision applies to all Work Objects in the Work Studio system. It does not apply to the component ledger's status model (`active`, `proposed`, `under-review`, `deprecated`), which is a separate grilling target. It does not apply to non-Work-Object lifecycles in the broader PKM system (Regulation Sessions, Study Sessions, Projects).

Enforcement is currently prose/agent-compliance through the conductor skill and specialist contracts. Planned enforcement is a CLI that validates state and status enum membership, enforces the two prohibited transitions, checks the five prerequisite gates against evidence entries with structural field-value matching, and surfaces type-specific progressions as advisory guidance. The CLI will not enforce a transition matrix, re-entry rules, state-status combination restrictions, or type-specific mandatory paths.

Revisit this ADR when the CLI design/build session produces a concrete implementation plan that differs from the lifecycle model defined here, when real Work Object usage demonstrates a pattern that the permissive model cannot represent, when a prerequisite gate is found to block legitimate work, or when a `high`-consequence Work Object exercises the untested close-routing gate and reveals a gap.

The lifecycle model was accepted across two grilling sessions — the architecture sweep (Decisions 1–32) and the Lifecycle & State Machine deep grilling (Decisions 33–44) — with the CLI-status clarification (Decision 45) establishing that enforcement is deferred. The state and status reductions were validated against real Work Object usage: 14 of 15 real objects already followed the reduced model in practice, with `decide`, `frame`, and `blocked` never used.
