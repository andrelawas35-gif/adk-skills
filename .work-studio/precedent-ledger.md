## R-001 — segmentation-masked-regional-revision

- **status:** validated
- **kind:** recipe (image revision)
- **purpose:** correct a regional flaw in an existing asset image (e.g.
  background clutter) while leaving the rest of the asset pixel-identical.
  [system, Decision 16]
- **applicable_when:** medium: image; subject: a generated asset reference
  image (prop/environment element); desired_effect: isolate/clean a specific
  region without disturbing the rest of the composition. [system, Decisions 9,
  11, 16 -- domain and subject drawn from the WO's asset-generation scope, not
  from Decision 16's text alone]
- **avoid_when:** the flaw is whole-frame / whole-object rather than regional
  -- a foreground-only or background-only mask leaves a whole-frame flaw only
  half-corrected. [system, Decision 17 -- not stated in Decision 16 itself]
- **inputs:**
  - source_image (the flawed before-image)
  - mask (silhouette-accurate, generated by `rembg`/u2net from the source
    image, not hand-drawn)
  - revision prompt (text description of the corrected region)
- **operations:**
  1. Generate a silhouette-accurate segmentation mask via `rembg` (u2net
     model), standalone script, not a ComfyUI custom node.
  2. `VAEEncodeForInpaint` with `grow_mask_by: 0`.
  3. `KSampler`, denoise 1.0.
  4. `FluxGuidance`, 3.5.
  5. Fixed seed (42 in the validated run).
  [system, Decision 16 -- all five steps and parameter values are directly
  stated]
- **prompt_template:** `[gap]` -- Decision 16's own text does not reproduce
  the literal prompt string used. It names the *category* ("background-only
  revision prompt") but not the exact text. The actual prompt exists only in
  the scratchpad Python script that submitted the ComfyUI job, which is
  external to the Work Object's Markdown record.
- **negative_constraints:** `[gap]` -- same reason; Decision 16's prose does
  not state whether a negative prompt was used or what it said (separately
  known from other evidence in this session that this pipeline used
  `ConditioningZeroOut`, i.e. no functional negative prompt at `cfg: 1.0` --
  but that fact is not present in Decision 16's own text, so it is marked as a
  gap for this tracer's purposes rather than pulled in from outside the
  bounded source).
- **verification:** background clutter (crates, rope, fabric, text) fully
  removed and replaced with plain neutral background across the whole frame;
  no visible seam; no protected-region identity drift. [system, Decision 16]
- **known_limits:** `rembg`'s u2net model can drop thin/wiry elements (e.g. a
  hanging chain) as background noise during segmentation, leaving a small
  unprotected sliver that gets filled with a minor cosmetic artifact -- a
  small, localized gap, not the systemic seam/leak failure this recipe fixes.
  [system, Decision 16]
- **provenance:**
  - derived_from: `2026-08-23-007` Decision 16 (primary; pass)
  - precursor (falsified) attempts: Decisions 12, 13, 15 (hand-drawn masks,
    all failed at the same root cause -- mask shape/precision)
  - generalization evidence: Decision 17 (partial results on other cases,
    establishes the avoid_when boundary above)
- **first validated:** 2026-08-24 (`2026-08-23-007` Decision 16)

## R-002 — single-view-image-to-3d-mesh-turnaround

- **status:** validated
- **kind:** recipe (3D asset generation, not 2D image revision)
- **purpose:** guarantee turnaround-view identity consistency for an asset by
  generating it as an actual 3D mesh, then deriving every needed view (front/
  back/left/right) as a camera rotation of that one mesh, instead of
  independently generating each 2D view and hoping they agree. [system,
  Decision 24]
- **applicable_when:** the asset needs multiple consistent views of the same
  object (turnaround, reference set) and a single concept image already
  exists; production-quality surface texture is not required yet
  (shape-only). [system, Decision 24 + revisit trigger]
- **avoid_when:** the deliverable needs actual textured material/surface
  detail immediately -- full shape+texture generation needs ~20GB+ VRAM,
  which does not fit the RTX 3080's 10GB. Also avoid if only one fixed view is
  ever needed (no turnaround requirement at all -- the extra mesh-generation
  step buys nothing). [system, Decision 24 revisit trigger]
- **inputs:**
  - one concept image (background-removed via `rembg` and composited onto a
    plain white background -- required, not optional; see known_limits)
  - Hunyuan3D-2 checkpoint (`hunyuan3d-dit-v2.safetensors`, native ComfyUI
    support, single-view/shape-only variant)
- **operations:**
  1. Remove the concept image's background (`rembg`) and composite onto
     white.
  2. Generate one 3D mesh from that image via native ComfyUI Hunyuan3D-2.
  3. Import the mesh into Blender.
  4. Render any needed view (front/back/left/right) as a camera rotation of
     the single imported mesh.
  [system, Decision 24 -- all four steps directly stated]
- **prompt_template:** N/A -- unlike R-001, this recipe has **no text-prompt
  conditioning step at all**. Hunyuan3D-2 conditions purely on the input
  image; there is nothing to gap here because there is no prompt in the
  mechanism, not because the Decision record omitted one.
- **negative_constraints:** N/A -- same reason as `prompt_template` above.
- **verification:** front/back/any-angle renders are structurally identical
  in shape, proportions, and fine detail (same panel divisions, same roof/base
  geometry), because they are camera angles on one 3D object rather than
  independently sampled 2D images -- identity is guaranteed by construction,
  not probabilistically achieved. [system, Decision 24]
- **known_limits:** (1) shape-only -- no texture/material stage fits the 10GB
  VRAM budget; texturing must happen separately (Blender render passes ->
  ComfyUI compositing, plan §5.3), not in this recipe. (2) The input image
  MUST have its background removed first -- the first attempt, using a raw
  photo, baked an unwanted flat background plane into the 3D geometry itself;
  only the background-removed, white-composited input produced a clean mesh.
  [system, Decision 24]
- **provenance:**
  - derived_from: `2026-08-23-007` Decision 24 (primary; pass)
  - superseded approach: Decisions 20, 23 (Flux Redux reference-locking --
    fixed object identity but never solved the viewpoint problem; Decision 24
    reframes the problem entirely rather than fixing Redux further)
- **first validated:** 2026-08-24 (`2026-08-23-007` Decision 24)

## Tracer bullet result

**Exit criteria evidence:** Six of nine Recipe fields (purpose, applicable_when
partially, operations, verification, known_limits, provenance, status)
populated cleanly and traceably from existing Decision prose with zero
fabrication. **Two fields (prompt_template, negative_constraints) could not be
honestly populated from Decision 16's text alone** -- the assumption that
Decision prose alone carries every Recipe field does not fully hold. The exact
prompt string and negative-conditioning approach are recorded only in the
scratchpad script artifacts referenced by the Decision, not in the Decision's
own narrative text.

**What this means:** harvesting is viable for the *method/parameter/outcome*
fields (the majority of the schema), but a harvester that reads only Decision
prose will systematically gap the literal prompt text on every entry. Two
options for the next (real harvester) step: (a) accept the gap -- prompt_template
stays `[gap]` unless a human fills it in by hand, or (b) extend the harvester to
also read the scratchpad script(s) a Decision's evidence entry points at (where
one exists) and extract the literal prompt from there.

**Second extraction (R-002, `2026-08-23-007` Decision 24) refines this
finding rather than just repeating it.** All 9 fields populated -- but
`prompt_template`/`negative_constraints` are marked **N/A, not `[gap]`**,
because this recipe's mechanism (image-to-3D-mesh) has no text-prompt step at
all. The R-001 gap was specific to *prompt-based* recipes (2D image
generation/revision), not universal across every recipe kind. This narrows
the harvester requirement: it must distinguish "no prompt in this mechanism"
(N/A, no work needed) from "a prompt exists but wasn't captured in Decision
prose" (`[gap]`, needs either acceptance or scratchpad-reading to fill) --
conflating the two would either wrongly flag N/A recipes as incomplete, or
wrongly assume a gapped prompt-based recipe has nothing missing.

Recording this as the riskiest-assumption result for the design tracer
accepted on WO `2026-08-23-001`.
