## How Default Entry Point Mode Works

### Before Step 5 (Explicit Invocation)

```bash
# User must remember to invoke explicitly
/orchestrate "render a preview for shot 14"
```

### After Step 5 (Default Entry Point)

```bash
# Any request automatically routes through orchestrator first
"render a preview for shot 14" → orchestrator classifies → routes to production skill
```

### Platform Adapter Flow

```mermaid
graph TD
    A[User Message] --> B[Platform Adapter]
    B --> C[Orchestrate Skill]
    C --> D{route_request()}
    D --> E[RoutingDecision Object]
    E --> F[Platform Adapter]
    F --> G{Invoke Target Skill}
    G --> H[Execute Work]
```

### Key Behaviors

1. **Implicit routing:** All messages go through orchestrator first
2. **Return-only pattern:** Orchestrator returns `RoutingDecision`, platform adapter handles invocation
3. **Cycle detection:** Platform adapter prevents infinite loops via call stack tracking
4. **Fallback logging:** Every LLM fallback is logged to evidence repository

---

## Architecture Decision: Return-Only Pattern

**Why not direct invocation?** See [platform-adapter-return-only-spec.md](../../deliverables/2026-08-25-003-platform-adapter-return-only-spec.md) for full rationale.

Key points:
- Prevents recursion when orchestrator routes to another skill that might route back
- Clear separation between classification (orchestrator) and execution (platform adapter)
- Testable units without mocking
- Future-proof against platform architecture changes
